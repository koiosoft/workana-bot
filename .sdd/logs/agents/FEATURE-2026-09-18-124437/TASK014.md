## Justification
Implemented all five spec items in `app/intelligence/adapters/openrouter.py`; no other file was touched.

**Imports (top of file).** Added `from pydantic import ValidationError`, `AIConnectionError, PipelineError` from `app.exceptions`, `RequirementAnalysis` from `app.models.analysis`, `TechnicalEstimateFull`/`TechnicalEstimateDiscovery`/`_assert_hours_consistent` from `app.models.estimate`, and `get_maturity_threshold` from `app.intelligence.config` — mirroring the import set already used by the Gemini adapter (TASK013) so both providers validate against the same models.

**(1) `analyze_requirement`.** Renders `s2-estimation/analyze-requirement.j2` with `full_description` (falls back to `description`) and `threshold=maturity_threshold`, selects the STANDARD model via `_select_model(self.flash_strategy)` + `_set_delay`, and calls the existing `_chat_completion` (which keeps its retry/backoff and circuit-breaker bookkeeping). Because OpenRouter may ignore `response_mime_type`, validation is deliberately **post-hoc**: the raw text is unwrapped by the new `_extract_json_object` helper (same ```json fenced-block / brace-slice heuristic already used by `generate_proposal`, so behaviour cannot drift between the two paths), parsed with `json.loads`, then run through `RequirementAnalysis.model_validate`. Three conditions raise `PipelineError`: empty text (`"LLM returned no text"`), `json.JSONDecodeError`, and `pydantic.ValidationError` — each logged and re-raised with `from e` so the cause chain survives. A network failure still surfaces as `AIConnectionError` (raised inside `_chat_completion` and re-propagated), i.e. infrastructure errors are not misclassified as guard-rail failures. On success returns `validated.model_dump(mode="json")`, so downstream stages see canonical field names/types rather than the model's raw prose.

**(2) `estimate_technical`.** Reads `branch = analysis.get("branch", "full")` and picks `s2-estimation/estimate-full.j2` vs `s2-estimation/estimate-discovery.j2` accordingly; the prompt receives `analysis_json=json.dumps(analysis, indent=2)`, matching the variable name both templates consume (and the Gemini adapter). Same post-hoc contract as Stage 1: `_extract_json_object` → `json.loads` → `TechnicalEstimateFull.model_validate` or `TechnicalEstimateDiscovery.model_validate`, with `PipelineError` on missing text / bad JSON / `ValidationError`. For the `full` branch only, `_assert_hours_consistent(validated)` runs afterwards so a `summary.total_hours` rollup mismatch is wrapped into a `ValidationError` and therefore into `PipelineError` instead of an unclassified crash — identical to TASK013.

**(3) `write_commercial_proposal`.** PREMIUM stage: renders `s3-commercial/write-proposal.j2` with `my_profile_skills`, `hourly_rate` (`HOURLY_RATE` env, same default as `generate_proposal`), `project_payload_json` and `technical_estimate_json=json.dumps(technical_estimate, indent=2)` — the template's own liability clause states it must not compute milestones/summary, and the code enforces that: after parsing the model reply, `milestones` and `summary` are re-injected **verbatim** from `technical_estimate`, so no numeric recomputation happens anywhere in this method (mirrors the Gemini implementation). Missing `questions_for_client` defaults to `[]`; empty text returns the same `{"error": ...}` dict shape the handlers already tolerate for `generate_proposal`; unparseable JSON raises `AIConnectionError` (Stage 3 has no Pydantic contract, so it is not a `PipelineError`).

**(4) `generate_project_fixed_proposal`.** Orchestrator added: resolves `threshold = get_maturity_threshold()` once, logs it, then awaits `analyze_requirement(project=…, maturity_threshold=threshold, circuit_breaker=…)` → `estimate_technical(project, analysis)` → `write_commercial_proposal(project, technical_estimate=estimate)` and returns the accumulated `{"analysis": …, "estimate": …, "proposal": …}` JSON. The abort requirement holds by construction: Stages 1/2 propagate `PipelineError` before the Stage 3 call site is reached, so PREMIUM is never billed on a guard-rail failure (verified by inspection of the call order — no `try/except` swallows it here; the Telegram handler owns error presentation). No repository writes exist in this method — persistence of `requirement_analyses`, `technical_estimates` and `proposal_versions` is left to TASK016 as specified.
