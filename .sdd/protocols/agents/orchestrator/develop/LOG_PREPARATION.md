### L-1: Prepare the log cycle with the CLI
- Run once at the start of the cycle. The `workflow open` subcommand takes a
  mode **flag**, not a bare protocol name. Use the flag that matches the current
  protocol (`${PROTOCOL}`):
  ```
  agent-instructor workflow open <FLAG>
  ```
- **Protocol → flag mapping** (pick the flag from this table; never pass the
  bare protocol name like `workflow open FEATURE` — that fails with
  `unrecognized arguments: FEATURE`):
  - `FEATURE` → `--feature`
  - `DEBUG` → `--debug`
  - `UPDATE-SPECS` → `--update-specs`
  - `BOOTSTRAP` → `--bootstrap`
- If no flag is supplied, `workflow open` defaults to a `FEATURE` cycle.
- Example: `agent-instructor workflow open --feature` opens the FEATURE cycle.

**CRITICAL — Execution rule:**
  - **When the user has explicitly requested a *new* cycle (per UI‑0), you MUST run `workflow open` without any prior state checks.** Do **not**:
  - Check whether `ACTIVE_CYCLE` exists.
  - Read the contents of any log directory.
  - Attempt to "resume" or "continue" an existing cycle.
  - The CLI itself will handle the case of an existing active cycle (e.g., by overwriting or erroring). If it errors, you follow the recovery in UI‑5 (reindex), **still without** analysing the situation. Your only responsibility is to execute the command.
  
- This command deterministically creates:
  - The log directory `.sdd/logs/agents/${PROTOCOL}-<TIMESTAMP>` (`LOG_DIR`).
  - `INDEX.md` with the protocol, date, time, objective, and the artifact table (columns `#`, `Agent`, `Model`, `Task`, `Status`, `Log`).
  - One `task-${i}.md` per pending `[ ]` task in the instruction file.
  - One `test-${type}-${i}.md` per pending `[ ]` test (type: unit, integration, or ui).
  - The `ACTIVE_CYCLE` pointer file that the `add` / `update` subcommands rely on.
- Capture the printed relative path as `LOG_DIR`.
- **Do NOT** create the directory, `INDEX.md`, or artifact files by hand. The CLI is the single source of truth for cycle creation.
- On success, return to the orchestrator phase that invoked this module via the `return_to_caller`
  label (see `sdd-lang.md` §2 — return labels). On a cycle binding mismatch, follow L-4
  (`workflow open --reindex`) and then return via the same label.

### L-2: Dynamic artifacts (recovery option)

- If a task or test needs to be added mid-cycle (e.g., discovered during execution), use the CLI against the active cycle:
  ```
  agent-instructor workflow add --task "<task>" [--agent <Agent>] [--model <Model>]
  agent-instructor workflow add --test --<unit|int|ui> "<test>" [--agent <Agent>] [--model <Model>]
  ```
- Each command appends the artifact file and an `INDEX.md` row with status `Pending`.
- This is an optional recovery mechanism, not the normal path (initial tasks/tests are already generated by L-1).

### L-3: Dynamic artifacts (DOD creation)

In addition to the artifacts created by L-1, `workflow open` also creates a
**Definition of Done (DOD)** document for every pending task:

- One `DOD-${TASK_ID}.md` per pending `[ ]` task, created in the same log
  directory as the corresponding `TASK_ID.md` (i.e., `${LOG_DIR}/DOD-${TASK_ID}.md`).
- The DOD contains the **ACK checklist** (acceptance criteria) for the task,
  copied from the instruction file's `## Acceptance Contract` section.
- The reviewer uses this file during review (see `dev-workers/DEV-REVIEWER.md` R-2).
- Workers (`sdd-worker`, `sdd-ui-worker`) receive **only** `TASK_ID.md` and never
  the DOD file (see ACK068).

This ensures every task has its acceptance criteria captured at cycle-creation
time, decoupling the review contract from the worker's implementation artifacts.

### Notes

- The orchestrator never reads the `task-${i}.md` / `test-*.md` files directly; it manages them only through the CLI.
- The `INDEX.md` Status column uses the textual values `Pending` / `In Progress` / `Completed` / `Failed`, managed exclusively via `update-status`.
- Retries reuse the same `task-${i}.md`. The responsible sub-agent writes its justification only on success.
